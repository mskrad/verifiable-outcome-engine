01

Overview

VRE commits the rules of an outcome on Solana before the result exists. Anyone can later recompute the result from the transaction signature, using only public RPC data, and compare it with what the program recorded.

What a MATCH proves

  • The rules did not change. Participants, weights or scores, formula and winner count are the exact bytes stored on-chain under the committed artifact hash, and that artifact was bound to the runtime before resolution.
  • The winners follow from the rules. Replaying the committed bytes with the randomness the program recorded yields the same winners, in the same order.
  • The records agree. Input, output, winner count, winner ids and effect digests match across the event, the resolution account and the replay.

What it does not prove

  • That the list was fair. VRE proves the list did not change after commit, not that it was complete or honest when committed.
  • That the operator could not foresee the result on every path. This depends on the randomness source; see §02.
  • That a prize was paid. Attestation paths prove the winners. Paying them is the integrator's step.

02

Resolution Model

Every path has the same shape: commit the rules, bind a runtime to them, resolve, replay.

  1. Commit. submit_compiled_artifact, init_compiled_artifact_chunk, write_compiled_artifact_chunk and finalize_compiled_artifact store the artifact bytes in chunk accounts keyed by their SHA-256. review_compiled_artifact, signed by the ProgramConfig admin, approves the artifact for binding.
  2. Bind. initialize_outcome_config creates a runtime, identified by runtime_id, bound to one artifact hash.
  3. Resolve. One of the paths in §06 writes an OutcomeResolution account and emits a resolution event.
  4. Replay. Any verifier rebuilds the artifact from its chunks, recomputes randomness and winners, and compares them with the records (§04).

03

Artifact Formats

Rules are serialized into a binary artifact that starts with the magic "W3O1" and a u16 format version. All integers are little-endian. An artifact is at most 8,192 bytes. Participant ids are printable ASCII, zero-padded to 64 bytes, and strictly ascending by bytes.

Artifacts resolved through rng_v2 must be payout-free: the header payout and every effect amount are zero. The program then records who won, and the integrator pays.

Selection rules

  • weighted_random. Round r takes a u64 from the first 8 bytes of the randomness when r = 0, and from SHA-256 of a domain tag, the randomness and r otherwise. It selects the entry whose cumulative weight covers u64 mod total_weight among entries not yet chosen.
  • rank_desc. Score descending, ties by order ascending.
  • rank_asc. Score ascending, ties by order ascending.
  • first_n. order ascending.
  • closest_to. |score − target| ascending, computed in 128 bits, ties by order ascending.
  • Compact winner digest. On rng_v2 the program binds the full winner list as winner_claim_hash = SHA256("VRE_RNG_V2_WINNERS" ‖ count_u16le ‖ Σ(len_u8 ‖ id_bytes)).

04

Verification

Given a transaction signature and a program ID, the verifier:

  1. Fetches the transaction logs and finds the resolution event emitted by that program. Conditions and slot events go to their dedicated replays.
  2. Loads the runtime's OutcomeConfig, the OutcomeResolution, the ApprovedOutcomeArtifact header and, for rng_v2, the RngV2State.
  3. Checks the artifact hash is the same in the event, config, resolution and header, and that the artifact is finalized with a status that allows binding.
  4. Rebuilds the artifact from its chunk accounts and re-hashes it.
  5. Recomputes the randomness: from master_seed for rng_v1, from the recorded slots and slot hashes for rng_v2, checking any operator reveal against its commitment.
  6. Replays winner selection. Compact artifacts replay the on-chain table; scale artifacts fetch the snapshot from its URI and check its hash, count and Merkle root.
  7. Compares input, output, winner count, winner ids and their padding, winner digest and effect digest. All equal: MATCH / OK. Otherwise the first failing check is returned as the reason.

Key separation

The upgrade authority can replace the code and nothing else. Both are single keys on devnet. Mainnet governance is decided separately and is not implied by the devnet setup.

Single-phase settle (v1.2) · default

prepare_rng_v2 fixes the rules, the stake and three future target slots, 8, 16 and 24 slots ahead. A Solana leader produces four slots in a row, so the first target is always at least two leader groups after the slot that included prepare, and the three targets fall in three different leader groups. Groups are not validators: one validator can lead several groups, and a skipped target moves to the next produced slot after the previous resolved one. A devnet draw on 2026-09-13 shows both: eight slots were skipped, targets ending 680, 688, 696 resolved to 688, 689, 696, and one validator produced all three. Measured over 5,000 recent slots on 2026-09-13: on mainnet one validator produced two of the three hashes in 3.1% of draws with these offsets, against 2.3% with 75/90/105, and never all three; on devnet, with 12 leaders and a 22.5% skip rate, one validator produced two or more in about 73% of draws and all three in about 10%, whatever the offsets. After the last target slot and before expiry, the same operator calls settle_rng_v2, which reads SlotHashes, derives the randomness, resolves the artifact and writes the resolution. The operator cannot predict the result. It can still choose not to settle; the prepared draw then remains visible on-chain and expires through expire_rng_v2, which refunds the stake. The public draw endpoints run this path in one request.

Two-phase seal and attest (v1.3.2)

  1. prepare — the operator opens the draw with a stake and a bounty.
  2. seal — seal_randomness is permissionless. Once the target slots land, anyone can seal, fixing the outcome and earning the bounty.
  3. attest — attest_winners, by the operator or the configured attester, records the resolution, takes the fee and refunds the rest of the stake.
  4. expire — a never-sealed draw expires and its bounty goes to the treasury; a sealed draw not attested by the deadline, 480 slots after expiry, can be closed by anyone with expire_sealed_rng_v2.

Use it when the operator has an interest in the result and must not be able to back out.

Compact artifacts on rng_v2

Since 2026-09-09 both rng_v2 lifecycles accept compact formats 1, 2, 3, 5 and 8, not only scale format 7. For compact artifacts the program selects the winners itself, so callers pass empty winner arguments; non-empty ones fail with RngV2CompactArgsMustBeEmpty. The resolution stores winner_claim_hash as the digest of the winner list, and the list is emitted in OutcomeResolvedV5. Scale artifacts keep caller-claimed winners proved by snapshot replay and emit OutcomeResolvedV4. Both must be payout-free. SDK 0.8.2 verifies these draws, and the public draw endpoints resolve through this path.

Sortition-by-Claim (v1.4.0)

Entrants register sha256(secret ‖ ticket_id ‖ draw_id) before a deadline. seal_sortition_draw fixes omega from three future slot hashes, 75, 90 and 105 slots after the draw was created; registration must close before the first of them. Each entrant claims by revealing the secret and wins when sha256(secret ‖ omega) < threshold.

  • Cost. A claim uses about 8,200 CU, under the 10k budget.
  • Coverage. 5 of 5 negative cases rejected.
  • Distribution. 200 draws of 100 tickets with 10 expected winners: mean 9.7, variance 8.76, against a binomial mean of 10 and variance 9.

Winners claim for themselves, so the operator pays nothing per winner. Fits airdrops, allowlists and mass rewards.

Sortition economics (v1.4.1)

An optional fee layer, byte-compatible with 1.4.0 draws. fee_mode selects an entry_fee_lamports at registration and a close_skim_bps skim at close. close_split(rent, skim_bps) guarantees refund + skim == rent. Measured: paid register 18,096 CU, init economics 5,234 CU, close 9,643 CU, sweep of two tickets 18,459 CU; 9 of 9 negative cases rejected.

Conditions (fc7)

Scores committed prediction slips, each a set of legs with odds, against revealed match facts, and ranks entrants. The off-chain scorer at POST /api/conditions/score is byte-identical to on-chain resolve_conditions, which uses about 15,700 CU. The event ConditionsResolvedV1 carries winners_digest, facts_ref_root and winning_score_sum. VRE proves the ranking; payout stays with the partner.

Slot spins (SF1)

prepare_slot_spin binds the player, the bet and the committed game before the entropy exists. settle_slot_spin derives randomness from future slot hashes, replays the reels from the artifact, applies the max-win cap and pays the bound player from the vault. The public demo game runs on its own devnet program, 6R5n5uPTj1bg4xz6P3xCmVkyorTySbLQQZuENe8SSaKK; verify its spins with the SDK and that program ID.

Unicorn-G entropy (B8) · implemented, not deployed

An alternative entropy source: a VDF output verified on-chain with an embedded Groth16 verifier. It was measured on devnet in June 2026: seal with verification 247,476 CU, attest 61,466 CU, and a wrong proof rejected as InvalidUnicornGProof. Its instructions sit behind a build feature that the canonical program is not built with. Before mainnet it needs the circuit soundness fix and a trusted-setup ceremony.

07

HTTP API

Base URL https://verifiableoutcome.online. JSON in, JSON out. Draw endpoints sign with the server's operator key, so callers never hold one. A draw resolves through rng_v2 inside the request: the server commits the rules, waits for the future target slots, about 10 seconds, then settles and replays, so a draw call takes 12–45 seconds in total.

The canonical program binds only artifacts approved by the ProgramConfig admin, so a draw cannot be resolved there with your own wallet; the API runs it with the operator key. Sortition instructions need no admin and can be sent from any funded wallet (§08).

Partner draw fields

  • formula. weighted_random, rank_desc, rank_asc, first_n or closest_to.
  • participants. At least 2 objects with a unique id of up to 64 printable ASCII bytes, plus weight or score as the formula needs. The compact artifact holds about 100 entries; use the snapshot flow above for more.
  • winners_count. 1 to 10, not more than the participants.
  • target. Required for closest_to; a signed safe integer.
  • use_case. raffle, airdrop or competition; informational.
  • Scale-shaped body. mode: "scale", scale: true, public_proof: true or standard_version: "1.2" on this endpoint returns 409 with route: "scale_snapshot" and the snapshot endpoints.
  • artifact_slot. The slot where these exact rules were first committed; identical rules reuse one artifact, so it can predate the draw.

SDK

verifiable-outcome-sdk is the TypeScript library for building artifacts and verifying outcomes. It is an ES module for Node 18 and later.

npm install verifiable-outcome-sdk # 0.8.2

Verify from a terminal

npx -p verifiable-outcome-sdk vre verify --sig <signature> [--rpc <url>] [--program-id <id>] [--json] # exit code 0 on MATCH, 1 otherwise

Verify a transaction

import { verifyOutcome } from "verifiable-outcome-sdk"; const result = await verifyOutcome({ signature: "<transaction signature>", rpcUrl: "https://api.devnet.solana.com", programId: "6QtLot4uztCfjUuPreoiYPc3e1gH2fg6pq8hKYyvCP6B", }); // { status: "MATCH", reason: "OK", outcome_id, outcome_ids, … }

Build an artifact

import { buildArtifact } from "verifiable-outcome-sdk"; const bytes = buildArtifact({ type: "formula_draw_v5", formula: "rank_desc", input_lamports: 10, payout_lamports: 0, winners_count: 2, participants: [{ id: "alice", score: 10 }, { id: "bob", score: 30 }], }); // Buffer with the fmt 5 artifact; its SHA-256 is the compiled_artifact_hash
