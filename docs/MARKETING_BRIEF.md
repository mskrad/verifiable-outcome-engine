## 1. TL;DR за 30 секунд

**VRE — это протокол на Solana, который делает результат розыгрыша/конкурса/раздачи
доказуемым.** Правила фиксируются on-chain **до** розыгрыша. После розыгрыша любой человек
берёт подпись транзакции и локально переигрывает результат — если совпало, получает `MATCH / OK`.

- **Один продающий факт:** оператор физически не может изменить правила или победителя после
  фиксации артефакта.
- **Одна команда для проверки:** `vre verify --sig <TX>` → `MATCH / OK`.
- **Одна команда для интеграции:** один `POST /api/partner/draw` — и партнёр получает
  подпись транзакции + публичную ссылку на проверку. SDK не обязателен.
- **Стадия:** живой канонический протокол на **Solana devnet**, есть один боевой партнёр
  в production (OddSol), mainnet — отдельный, более поздний этап.

## 2. Проблема, которую решает продукт

Любое Solana-приложение, которое кого-то выбирает — розыгрыш, airdrop, whitelist, торговый
конкурс, лут-дроп, prediction market — в конце объявляет победителя. Сегодня пользователь
обязан **поверить бэкенду оператора**. Чем больше денег в розыгрыше, тем больше разрыв доверия.

Формулировка проблемы для лендинга и питчей:

> «Каждый проект говорит "розыгрыш честный". Никто не может это проверить.
> Победителя объявляет тот же, кто его выбирал.»

Типовые последствия для проектов (то, что маркетолог продаёт как боль):

| Боль | Как проявляется |
|---|---|
| Обвинения в подкрутке | Комьюнити считает, что победители — «свои кошельки» |
| Падение конверсии в участие | Люди не заходят в розыгрыш, которому не верят |
| Репутационный кризис постфактум | Одна спорная раздача обнуляет доверие к бренду |
| Невозможность оправдаться | Нет артефакта, который можно предъявить как доказательство |

VRE закрывает разрыв не обещанием, а **воспроизводимостью**: доказательство лежит в публичных
данных Solana, и проверить его может любой сторонний человек, а не только оператор.

## 3. Что именно продукт гарантирует (и чего НЕ гарантирует)

Это самый важный раздел брифа. Здесь легко переобещать и получить справедливую критику от
крипто-аудитории. Формулировка гарантии из `ROADMAP.md` — дословно:

> **Гарантия:** Результат был получен применением фиксированного алгоритма к заранее
> зафиксированному артефакту, с использованием on-chain-случайности из резолвящей транзакции.
> Оператор не мог изменить ни правила, ни результат после фиксации артефакта.

**Чего VRE НЕ гарантирует:**

- ❌ **Что список участников честный.** VRE доказывает, что *шаг выбора* не подкручен. Если
  оператор набил список своими кошельками до фиксации — VRE это не ловит.
- ❌ **Что деньги дошли до победителя.** В режиме `conditions` VRE вообще не держит средства
  (no fund custody): он доказывает ранжирование, выплату делает партнёр.
- ❌ **Продакшн-гарантию на реальные деньги.** Канонический деплой — devnet. Mainnet — отдельный
  этап.
- ❌ **Что факты извне верны.** В `conditions` факты берутся из источника партнёра (TxLINE);
  VRE привязывает ссылку на факты (`event_stat_root`), но сам их не перепроверяет.

**Как это подавать в маркетинге, не теряя силу сообщения:**
честность про границы здесь работает *в плюс* — это язык, который крипто-аудитория уважает.
Рекомендуемая формула: «Мы не просим верить нам. Мы доказываем ровно одну вещь — и говорим
прямо, какую именно.»

## 4. Как это работает — объяснение без технического жаргона

Метафора для лендинга и видео:

> **Запечатанный конверт с правилами.** Перед розыгрышем оператор кладёт в блокчейн запечатанный
> конверт: полный список участников, их веса, формулу выбора. Конверт нельзя подменить — он
> уже в цепочке, с отметкой слота. Потом происходит розыгрыш, и случайность берётся не из
> кармана оператора, а из будущего блока Solana. После этого любой желающий берёт конверт,
> берёт случайность из цепочки, прогоняет ту же формулу у себя на ноутбуке — и получает того
> же победителя. Совпало → `MATCH`.

Три события, которые видит пользователь:

```
1. COMMIT   → правила зафиксированы on-chain (артефакт + хэш), слот X
2. RESOLVE  → программа выбирает результат детерминированно,   слот Y > X
3. VERIFY   → любой переигрывает из публичных RPC-данных     → MATCH / OK
```

Визуальный аргумент, который стоит выносить на первый экран: **`committed at slot X` <
`resolved at slot Y`** — видно, что правила зафиксированы *раньше* розыгрыша. Это «доказательство,
которое видно глазами», а не только в CLI.

## 5. Продуктовые поверхности (что вообще можно продавать)

| Поверхность | Что это | Кому | Нужен ключ? |
|---|---|---|---|
| **Verify-страница** `/verify` | Вставил подпись → `MATCH / OK` | Конечные пользователи, комьюнити | Нет, бесплатно всегда |
| **npm SDK** `verifiable-outcome-sdk` | `verifyOutcome()`, `buildArtifact()` | Разработчики | Нет |
| **CLI** `vre verify` / `vre resolve` | Проверка и оператор-резолв из терминала | Разработчики, ревьюеры | Нет для verify |
| **Partner Draw API** `POST /api/partner/draw` | Один HTTP-запрос → подпись + replay-URL | B2B-партнёры без блокчейн-команды | Да, `x-api-key` |
| **Sortition API** `/api/partner/sortition/*` | Commit-reveal-розыгрыш с self-claim | Массовые розыгрыши | Да |
| **Conditions API** `/api/conditions/score` + `/api/partner/conditions/*` | Скоринг прогнозных купонов → ранжирование | Prediction / parlay-платформы | score — нет, commit/resolve — да |
| **Встраиваемый виджет** `widget.js` | `<vre-verify>` / `<vre-verify-form>` на чужой странице | Проекты, которым нужен «знак проверки» у себя | Нет |
| **Partner instance** | Свой program ID, `fee_lamports = 0` | Крупные платформы, GameFi, NFT-маркетплейсы | Коммерческий договор |

**Ключевой маркетинговый рычаг — виджет.** Это единственная поверхность, которая живёт на
странице *партнёра* и постоянно показывает бренд VRE конечным пользователям. Дистрибуция
через виджет = органический рост узнаваемости.

## 6. Режимы резолюции (что технически умеет протокол)

Всё работает на **одной** канонической devnet-программе `6QtLot…`.

| Путь | Версия | Статус | Простыми словами |
|---|---|---|---|
| Replay-by-signature + global-Ω | v1.3.2 | **канонический, по умолчанию** | Основной сценарий: переиграть результат по подписи транзакции |
| Sortition-by-Claim | v1.4.0 | канонический | Билетный розыгрыш: участник сам заявляет выигрыш, раскрыв секрет |
| Sortition economics | v1.4.1 | канонический | Опциональный слой комиссий: плата за вход + ским при закрытии |
| Conditions (OddSol) | fc7/fv9 | канонический, только аттестация | Скоринг прогнозных купонов (коэффициенты × доказанные факты) → рейтинг |
| Unicorn-G entropy | B8 | **opt-in, research** | Альтернативный источник энтропии (VDF + Groth16). **Не для mainnet** |
| `settle_rng_v2` | v1.2 | канонический | Однофазный быстрый резолв для казино/игр |

**Формулы выбора победителя** (то, что реально продаётся как «сценарии»):

- `weighted_random` — взвешенный случайный выбор одного или N победителей
- `rank_desc` / `rank_asc` — топ (или низ) по счёту
- `closest_to` — ближайший к зафиксированной цели
- `composite_rank_desc` — многополевой взвешенный композитный счёт
- `first_n` — первые N по порядку регистрации

**Про Unicorn-G — осторожно.** Есть известная оговорка по стойкости (составное `l` проходит
in-circuit проверку простоты) и trusted setup на devnet-модуле RSA. В маркетинге: либо не
упоминать вовсе, либо только как «исследовательское направление». **Никогда** — как готовую фичу.

## 7. Целевые аудитории (ICP) и их Jobs-to-be-Done

### Сегмент A — Разработчик Solana-dApp (текущее ядро)
- **Кто:** инди-разработчик или команда 2–10 человек, делает розыгрыш/минт/конкурс.
- **JTBD:** «Мне надо провести розыгрыш так, чтобы потом не оправдываться в Discord.»
- **Триггер входа:** пост в X / GitHub / npm-поиск по `solana raffle verifiable`.
- **Путь активации:** verify-страница → блессед-подпись → `npm install` → первый свой draw.
- **Возражение:** «Мне проще написать `Math.random()` на бэкенде.»
  **Ответ:** «Пока не спросят. Один спорный розыгрыш стоит дороже, чем один POST-запрос.»

### Сегмент B — B2B-платформа без блокчейн-команды (главный коммерческий сегмент)
- **Кто:** биржа, трейдинг-платформа, GameFi-проект, NFT-маркетплейс, launchpad.
- **JTBD:** «У нас есть лидерборд и призовой фонд. Нужно доказательство честности, но выделять
  блокчейн-разработчика мы не будем.»
- **Крючок:** Partner Draw API — **один POST**, никакого SDK, никаких ключей на их стороне.
  VRE делает всю on-chain-работу своим ключом.
- **Доказательство:** OddSol — живая production-интеграция через VRE-operated endpoints.
- **Возражение:** «Мы не хотим отдавать ключи / деплоить контракт.»
  **Ответ:** «И не надо. Вы вызываете HTTP-эндпоинт с `x-api-key`. Ключи и деплой — на нашей стороне.»

### Сегмент C — Крупная платформа (Partner instance)
- **Кто:** платформа с большим объёмом резолвов.
- **JTBD:** «Нужен свой program ID, свой admin-кошелёк, без покомиссионной модели.»
- **Оффер:** выделенный инстанс, `fee_lamports = 0`, доступ к исходникам программы,
  поддержка развёртывания — по коммерческому договору.
- **Продающая деталь:** публичная проверка остаётся той же — любой может запустить
  `vre verify` против *их* program ID. Приватный инстанс не ломает публичное доказательство.

### Сегмент D — Конечный пользователь / участник розыгрыша (не покупатель, но амплификатор)
- **JTBD:** «Я проиграл. Меня кинули или нет?»
- **Поверхность:** verify-страница и виджет на сайте партнёра.
- **Роль в маркетинге:** этот сегмент не платит, но именно он создаёт давление на проекты
  («а у вас розыгрыш проверяемый?»). Стоит строить контент прямо для него —
  это классический bottom-up-заход.

### Сегмент E — Prediction / parlay-платформы (доказанный вертикальный кейс)
- **Кто:** проекты в духе OddSol — купоны, коэффициенты, ранжирование.
- **JTBD:** «Нужно доказать рейтинг победителей, не отдавая деньги в кастодиан.»
- **Аргумент:** off-chain-скорер байт-в-байт совпадает с on-chain `resolve_conditions`.
  Живая аттестация переигрывается в `MATCH`.

## 9. Конкурентное позиционирование

**Главная ошибка, которой надо избежать: VRE — это НЕ VRF.**

| Категория | Примеры | Что делают | Отличие VRE |
|---|---|---|---|
| **VRF / источники случайности** | Chainlink VRF, Switchboard, ORAO VRF, Pyth Entropy | Дают проверяемое случайное число | VRE доказывает **весь исход целиком**: правила + список + формула + случайность → конкретный победитель |
| **Оракулы фактов** | Pyth, Switchboard feeds | Приносят внешние данные on-chain | VRE привязывает ссылку на факты, но не является источником фактов |
| **Самописный бэкенд** | внутренняя логика проекта | Быстро и бесплатно | Не проверяется никем снаружи; это и есть проблема |
| **«Честность на слово»** | пост в Discord со скриншотом | Ноль затрат | Ноль доказательной силы |

**Позиционная формула:**

> «VRF даёт вам случайное число. VRE даёт вашим пользователям доказательство того,
> **что именно вы с этим числом сделали**.»

Это отдельная категория: **verifiable resolution layer** / **outcome attestation layer**.
Категорию стоит занимать явно — свободна и точно описывает продукт.

**Дополнительный дифференциатор:** порог входа. Конкуренты требуют интеграции на уровне смарт-
контракта. VRE в B2B-режиме требует **одного HTTP-запроса**, потому что on-chain-часть выполняет
сам VRE своим ключом.

## 10. Монетизация

Три модели, как они описаны в репозитории:

1. **Protocol fee за резолв.** Каждый вызов `resolveOutcome` на канонической программе может
   собирать комиссию в казну VRE (`ProgramConfig.fee_lamports`). Меняется админом без апгрейда
   программы.
   ⚠️ **Текущее значение: 0 лампортов на devnet.** То есть выручки по этой модели сейчас нет.
2. **Partner instance (коммерческий договор).** Выделенный деплой: свой program ID, `fee_lamports = 0`,
   доступ к исходникам программы, поддержка развёртывания. **[НЕТ ДАННЫХ]** по цене/условиям.
3. **Партнёрские API-ключи с тирами.** В `config/partners.json` у партнёров есть поле `tier`
   (в примере — 0 и 1) и флаг `draw_enabled`. Структура под тарификацию заложена, но
   **публичного прайса не существует** — **[НЕТ ДАННЫХ]**.

**Что бесплатно всегда и должно так и коммуницироваться:** верификация. `/api/replay`, SDK-verify,
страница `/verify`, виджет. Это осознанный выбор — бесплатная проверка и есть маркетинговый
двигатель: чем больше людей проверяет, тем выше давление на проекты интегрироваться.

**Вывод для маркетолога:** сейчас это **не revenue-стадия, а adoption-стадия**. Метрика успеха
кампаний — количество интеграций и проверок, а не деньги.

## 13. Позиционирование и сообщения

### Текущий позиционирующий слоган (уже на сайте)
- **«On-chain proof of who won.»** / «Prove Outcomes. Earn Trust.»
- Расширение: «Trust is a resource. VRE helps you earn it.»

Слоган сильный: короткий, конкретный, не обещает лишнего. **Рекомендую сохранить** и строить
всё остальное вокруг него.

### Мессадж-хаус

**Крыша:** Доверие можно не просить, а доказать.

**Три несущие колонны:**

1. **Правила зафиксированы раньше розыгрыша.**
   Доказательство: `committed at slot X < resolved at slot Y` — видно в цепочке.
2. **Проверяет кто угодно, не только вы.**
   Доказательство: `vre verify --sig <TX>` → `MATCH / OK`, бесплатно, без кошелька и без ключа.
3. **Интеграция за один запрос.**
   Доказательство: `POST /api/partner/draw` → подпись + replay-URL. Без SDK, без деплоя,
   без ваших ключей.

**Фундамент (доказательства):** 4 живые devnet-подписи, боевой партнёр OddSol,
регистрация в Metaplex Agent Registry, публичный evidence-пакет, открытый SDK на npm.

### Заготовки формулировок под разные каналы

**Твит-хук (для сегмента D, конечных пользователей):**
> Вы проиграли в розыгрыше. Как узнать, был ли он честным?
> Обычно — никак. Организатор объявил победителя, и всё.
> Есть другой путь: правила фиксируются в блокчейне до розыгрыша, и любой человек может
> переиграть результат сам. Одна команда — и вы знаете точно.

**Питч для B2B (сегмент B, холодное письмо):**
> У вас лидерборд и призовой фонд. Ваши пользователи верят результату на слово.
> VRE делает результат проверяемым: вы отправляете один POST-запрос со списком участников и
> формулой, получаете подпись транзакции Solana и публичную ссылку. Любой ваш пользователь
> может убедиться сам. Никакого SDK, никакого деплоя, ваши ключи остаются у вас.

**Для разработчика (сегмент A, README/npm/dev-канал):**
> `npm install verifiable-outcome-sdk`
> `vre verify --sig <TX>` → `MATCH / OK`
> Правила коммитятся до розыгрыша. Реплей идёт из публичных RPC-данных. Бэкенду верить не нужно.

**Ответ на «зачем, если есть VRF»:**
> VRF даёт случайное число. Он не доказывает, что вы применили его к тому списку участников,
> который обещали. VRE фиксирует список, веса и формулу *до* розыгрыша — и доказывает весь
> путь до конкретного победителя.

## 14. Воронка и путь активации

```
ОСВЕДОМЛЁННОСТЬ   → тред в X / пост в Solana-сообществах / кейс OddSol
        ↓
ИНТЕРЕС           → /verify: вставил готовую подпись → MATCH за 5 секунд  ← «момент ага»
        ↓
ОЦЕНКА            → /examples и /play: четыре живых сценария, клик → проверка
        ↓
ПРОБА             → npm install + первая своя подпись ИЛИ демо-ключ Partner API
        ↓
ИНТЕГРАЦИЯ        → виджет на своей странице (здесь начинается органическая дистрибуция)
        ↓
КОММЕРЦИЯ         → partner instance / платный тир
```

**Ключевой инсайт по воронке:** «момент ага» наступает **до** любой регистрации. Человек может
вставить подпись и увидеть `MATCH` без кошелька, без ключа, без установки. Это редкость для
крипто-инфраструктуры и главный конверсионный актив — вокруг него нужно строить весь трафик.

**Главное узкое место воронки** (стоит проверить): от «увидел MATCH» до «сделал свой первый
draw» дистанция велика — нужен либо funded devnet-кошелёк, либо партнёрский ключ, который
выдаётся вручную через письмо. Это ручной шаг с человеком в цикле. Если на нём теряется поток —
это первый кандидат на оптимизацию (self-serve выдача демо-ключа).

## 19. FAQ и работа с возражениями

**«Чем это отличается от VRF?»**
VRF даёт случайное число. VRE доказывает весь исход: список участников, веса, формулу и
случайность, зафиксированные до розыгрыша и приводящие к конкретному победителю.

**«Мне нужно доверять VRE?»**
Нет — в этом и суть. Проверка идёт из публичных данных Solana. Вы можете переиграть результат
своим кодом, не обращаясь к серверам VRE вообще.

**«А если оператор набьёт список своими кошельками?»**
VRE это не поймает и не утверждает обратного. Он доказывает, что *шаг выбора* не был подкручен
после фиксации правил. Честность формирования списка — отдельная задача.

**«Сколько стоит?»**
Проверка бесплатна всегда. Комиссия протокола за резолв сейчас **0 лампортов** на devnet.
Крупные платформы могут получить выделенный инстанс без покомиссионной модели по договору.
**[НЕТ ДАННЫХ]** по конкретным ценам — уточнить у команды.

**«Это работает на mainnet?»**
Пока нет. Канонический протокол живёт на devnet, mainnet — отдельный, более поздний этап
с собственной моделью управления (мультисиг / immutable / таймлок).

**«Насколько сложно интегрировать?»**
Для B2B — один POST-запрос с API-ключом. On-chain-часть выполняет VRE своим ключом.
Для разработчиков — `npm install verifiable-outcome-sdk` и две функции.

**«Сколько участников выдержит?»**
Сейчас — 2–10 с читаемыми ID, до ~20 с короткими. Большие списки через Merkle-снепшоты
разрабатываются. Это честное текущее ограничение, и его надо называть до того, как спросят.

**«Код открыт?»**
SDK — да, MIT, на npm. Исходники Solana-программы пока закрыты, открытие планируется после
запуска. Но развёрнутую программу можно верифицировать через IDL и on-chain-реплей без доступа
к исходникам.

## 21. Мои рекомендации по приоритетам

Если бы приоритизировал я, порядок был бы такой:

1. **Развернуть кейс OddSol в полноценный case study.** Единственная живая production-интеграция —
   это самый ценный неиспользованный актив. «Prediction-платформа доказывает рейтинг победителей
   on-chain, не отдавая деньги в кастодиан» — законченная история с проверяемой подписью.

2. **Сделать verify-страницу главной точкой входа для трафика.** «Момент ага» бесплатен,
   мгновенен и не требует регистрации. Вести на него весь платный и органический трафик,
   а не на главную.

3. **Self-serve демо-ключ.** Ручная выдача через письмо убивает воронку между интересом и пробой.
   Даже жёстко ограниченный автоматический ключ радикально изменит конверсию.

4. **Занять категорию явно.** Не соревноваться в поле VRF, а закрепить термин
   *verifiable resolution layer*. Категория свободна и точно описывает продукт.

5. **Не запускать масштабные B2B-кампании до снятия лимита на размер списка.**
   Лимит в 2–10 участников не переживёт первого же реального лидерборда — привлечённые лиды
   упрутся в него и уйдут с негативным впечатлением. Кампании — после Merkle-снепшотов.

6. **Строить контент для конечных пользователей.** Сегмент D не платит, но именно он создаёт
   вопрос «а ваш розыгрыш проверяемый?». Этот вопрос продаёт лучше любого аутрича.

## 22. Глоссарий

| Термин | Значение простыми словами |
|---|---|
| **Артефакт (artifact)** | Скомпилированный «конверт с правилами»: участники, веса, формула. Фиксируется on-chain до розыгрыша |
| **Commit** | Момент фиксации правил в блокчейне |
| **Resolve** | Момент розыгрыша: программа выбирает результат |
| **Replay / реплей** | Независимое повторение расчёта из публичных данных |
| **MATCH / OK** | Результат совпал с он-чейн — доказательство прошло |
| **MISMATCH** | Не совпало: неверная подпись, RPC или program ID |
| **Подпись транзакции (signature)** | Уникальный идентификатор транзакции Solana; входная точка проверки |
| **Program ID** | Адрес смарт-контракта в Solana |
| **Слот (slot)** | Отметка времени в Solana; доказывает, что коммит был раньше розыгрыша |
| **CU (compute units)** | Вычислительная стоимость операции; чем ниже, тем дешевле пользователю |
| **RPC** | Публичная точка доступа к данным блокчейна |
| **SlotHashes** | Хэши недавних слотов — источник случайности по умолчанию |
| **Devnet** | Тестовая сеть Solana. Не настоящие деньги |
| **Mainnet** | Основная сеть Solana. Настоящие деньги |
| **Sortition** | Розыгрыш, где участник сам заявляет выигрыш, раскрывая секрет |
| **Commit-reveal** | Схема: сначала фиксируешь хэш секрета, потом раскрываешь сам секрет |
| **No fund custody** | VRE не держит и не двигает деньги — только доказывает результат |
| **Merkle-снепшот** | Способ зафиксировать огромный список одним корневым хэшем |
| **Реплей-URL** | Публичная ссылка вида `/verify?sig=…`, которую можно дать кому угодно |
